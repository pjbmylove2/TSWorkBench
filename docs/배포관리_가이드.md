# 배포(릴리스) 관리 가이드

> 프로그램을 고치거나 새로 만들어 현장에 설치할 때, **코드 · 매뉴얼 · 이미지 · 배포 파일 · 설치 이력**을 함께 관리하는 방법.
> 사내 소스 서버가 없어도 **내 PC의 Git + 공유 폴더(NAS)** 만으로 현업 표준 방식을 그대로 쓸 수 있게 정리했습니다.

---

## 1. 한눈에 보기 — 현업 표준 4가지

| 무엇을 | 어디에 | 왜 |
| --- | --- | --- |
| **소스 코드 + 매뉴얼(글·이미지)** | Git 저장소 (프로그램마다 1개) | 누가 언제 무엇을 바꿨는지 이력이 남고, 어느 시점으로든 되돌릴 수 있다. 매뉴얼을 코드 옆에 두면 코드와 설명서 버전이 어긋나지 않는다 |
| **버전 표시** | Git 태그 `v2.4.2` + 프로그램 버전 번호 | "현장 2.4.2 소스가 뭐였지?"에 바로 답한다 |
| **배포 파일(실행 파일·DLL)** | 배포본 보관소 `\\NAS\Releases\프로그램\v2.4.2\` (변경 불가) | 한 번 내보낸 파일은 다시 만들지 않고 그대로 보관 → 롤백 = 이전 버전 폴더 설치 |
| **설치 이력** | TS WorkBench › 배포 이력 | "지금 그 설비에 어느 버전이 깔려 있나"를 바로 본다 |

흐름:

```
코드 수정 ─▶ 커밋 (TS-2026-10-0002 재연결 로직 수정)
          ─▶ CHANGELOG·버전 번호 올리기
          ─▶ Release 빌드
          ─▶ 배포 패키지 만들기 (TS WorkBench) → \\NAS\Releases\OmniSight\v2.4.2\
          ─▶ git tag v2.4.2 + git push (공유 폴더 저장소로 백업)
          ─▶ 현장 설치 → 업무 카드에서 [배포 기록]
```

## 2. 프로그램 저장소 구성 (프로그램마다 1개)

```
OmniSight\                     ← 저장소 최상위 (git init)
  src\                         코드 (.sln, 프로젝트)
  docs\                        매뉴얼 (Markdown 권장)
    사용설명서.md
    설치가이드.md
    images\                    화면 캡처·배선도·도면 (PNG/JPG)
  CHANGELOG.md                 버전별 변경 내역 (배포 노트의 원본)
  .gitignore                   bin\ obj\ .vs\ release\ *.user
  README.md                    빌드 방법, 폴더 설명
```

- **매뉴얼은 Markdown + images 폴더**: Word보다 변경 이력(diff)이 보이고, 그림은 `![설명](images/파일.png)`로 넣는다. 고객 제출용 PDF가 필요하면 배포할 때 만든다(VS Code·Typora 등에서 PDF 내보내기).
- **이미지 이름 규칙**: `화면_메인_v2.4.png`, `배선_카메라_2호기.jpg`처럼 내용을 알 수 있게. 공백 대신 `_`.
- **큰 파일(동영상, 수백 MB 설치 파일, 고객 원본 이미지)은 저장소에 넣지 않는다.** Git은 큰 바이너리를 다루기 어렵다. 보관소의 해당 버전 폴더 `manual\`이나 별도 공유 폴더에 두고 경로만 매뉴얼에 적는다.
- **고객사별 차이는 브랜치가 아니라 설정 파일로**: `Config\A사.json`, `Config\B사.json`처럼 같은 코드에 설정만 다르게. 고객사마다 브랜치를 만들면 수정할 때마다 여러 곳에 옮겨야 해서 반드시 어긋난다.
- 비밀번호·고객 원본 데이터는 저장소에 넣지 않는다 (`.gitignore`).

### CHANGELOG.md 예

```markdown
# 변경 내역

## 2.4.2 (2026-10-16)
- 카메라 연결이 끊기면 5초 간격으로 계속 재연결 (TS-2026-10-0002)
- 재연결 중 화면에 '카메라 재연결 중 (n회)' 표시

## 2.4.1 (2026-09-20)
- 검사 결과 이미지 저장 경로를 날짜별 폴더로 변경
```

## 3. 서버 없이 백업·이력 보관 — 공유 폴더 "bare 저장소"

사내 GitLab 같은 서버가 없어도, 공유 폴더에 Git 저장소를 하나 만들어 두면 `git push`로 이력째 백업됩니다.

**처음 한 번** (공유 폴더 `\\NAS\git`가 있다고 가정):

```bash
git init --bare "//NAS/git/OmniSight.git"
```

```bash
git remote add origin "//NAS/git/OmniSight.git"
```

```bash
git push -u origin main
```

**평소**: 커밋한 뒤 `git push`. PC가 고장 나도 `git clone "//NAS/git/OmniSight.git"`로 전부 되살아난다.

> 공유 폴더가 없으면 외장 디스크·OneDrive 폴더에 같은 방식으로 만들어도 됩니다.

## 4. 버전 번호 규칙

`주.부.수정` (예: 2.4.2)

| 올리는 자리 | 언제 | 예 |
| --- | --- | --- |
| 수정 (2.4.**2**) | 버그 수정, 설정 기본값 변경 | 재연결 로직 수정 |
| 부 (2.**5**.0) | 기능 추가, 화면 변경 (기존 설정 그대로 동작) | 검사 항목 추가 |
| 주 (**3**.0.0) | 설정 파일·통신 형식이 바뀌어 예전 것과 호환 안 됨 | PLC 프로토콜 변경 |

- 프로그램의 `AssemblyVersion`/`AssemblyFileVersion`(Properties\AssemblyInfo.cs)을 같은 번호로. 현장 PC에서 파일 속성만 봐도 버전을 알 수 있다.
- 배포할 때마다 Git 태그: `git tag -a v2.4.2 -m "OmniSight 2.4.2 배포"` → `git push origin v2.4.2`
- **커밋 메시지에 업무 ID**를 넣으면 업무 카드 ↔ 코드 변경이 이어진다: `TS-2026-10-0002 카메라 재연결 무한 재시도`

## 5. 배포본 보관소 (변경 불가)

```
\\NAS\Releases\
  OmniSight\
    v2.4.1\
    v2.4.2\
      OmniSight_v2.4.2.zip     실행 파일·DLL·설정 기본값 (Release 빌드 폴더 통째, .pdb 제외)
      manual\                  그 버전의 매뉴얼·이미지 (저장소 docs 폴더 복사)
      RELEASE_NOTES.md         변경 내역
      SHA256SUMS.txt           파일 무결성 확인용
```

- **한 번 만든 버전 폴더는 고치지 않는다.** 잘못 만들었으면 2.4.3으로 다시 만든다. 그래야 "현장의 2.4.2"와 "보관소의 2.4.2"가 항상 같은 파일이다.
- **롤백** = 이전 버전 폴더의 zip을 그대로 설치하고, TS WorkBench 설치 이력에서 해당 설치를 "되돌림"으로 표시.
- **SHA256SUMS.txt**: USB로 옮긴 파일이 깨지지 않았는지 현장에서 확인할 때.

```bash
certutil -hashfile OmniSight_v2.4.2.zip SHA256
```

  출력값이 SHA256SUMS.txt의 해당 줄과 같으면 정상.

TS WorkBench의 **배포 패키지 만들기**가 이 폴더를 자동으로 만들어 줍니다 (6장).

## 6. TS WorkBench로 하기

### 6.1 처음 한 번
1. **설정 › 배포본 보관소**에 `\\NAS\Releases` 지정 → 기본 정보 저장
2. **설정 › 기준 정보 › 프로그램 (배포용)**에 관리하는 프로그램 이름 등록 (예: OmniSight)

### 6.2 배포 패키지 만들기
1. 프로그램을 Release로 빌드 (`src\…\bin\Release`)
2. **배포 이력 › + 배포본 등록 · 패키지 만들기**
   - 프로그램, 버전(2.4.2) → Git 태그는 `v2.4.2`로 자동 입력
   - 빌드 폴더: `bin\Release`, 매뉴얼 폴더: 저장소의 `docs`
   - 관련 업무 ID: `TS-2026-10-0002`
   - 변경 내역: CHANGELOG의 해당 버전 내용 붙여넣기
3. `패키지 만들기` → 보관소에 `v2.4.2\` 폴더가 생기고, **git tag 명령이 클립보드에 복사**됨 → 소스 저장소에서 붙여넣어 실행

이미 다른 방법으로 만든 배포 폴더가 있으면 "이미 있는 배포본 등록만"을 선택해 경로만 기록합니다.

### 6.3 현장에 설치할 때
- 업무 카드 아래 **배포 기록** → 배포본 선택, 설치 일시 확인 → 저장
  - 카드의 고객사·사이트·설비·ID가 자동으로 들어감
  - 카드의 ③조치 › 변경 내역에 `배포: OmniSight v2.4.2 → 롤프레스 1호기 (일시) 배포본 경로`가 자동 기입, 작업 이력에도 남음
- 업무 카드 없이 설치했으면 **배포 이력 › 설비에 설치 기록**

### 6.4 조회
- **배포 이력 › 배포본**: 버전별 변경 내역, 보관소 경로, 설치한 설비 목록
- **배포 이력 › 설비별 현재 버전**: 설비마다 프로그램별 마지막 설치 버전 (되돌림 표시한 설치는 빠짐)
- **주간·월간 보고**에 "배포 (기간 내 설비 설치)" 표가 자동으로 들어감

## 7. 체크리스트 — 배포 한 번

- [ ] 변경 커밋에 업무 ID (`TS-…`)
- [ ] `CHANGELOG.md`에 이번 버전 내용
- [ ] `AssemblyVersion` 올림
- [ ] 매뉴얼(`docs`)·스크린샷 갱신 — 화면이 바뀌었으면 이미지도 다시 캡처
- [ ] Release 빌드, 사무실 테스트 (재현 데이터)
- [ ] TS WorkBench › 배포 패키지 만들기
- [ ] `git tag` + `git push` (태그 포함)
- [ ] 현장 설치 전 현재 버전 백업, 롤백 버전 폴더 확인
- [ ] 설치 후 업무 카드 › 배포 기록

## 8. 예제 (예제 데이터 폴더에 들어 있음)

| 배포본 | 변경 | 설치 |
| --- | --- | --- |
| OmniSight v2.4.1 (2026-09-20) | 이미지 저장 경로 날짜별 폴더, 로그 보관 기간 설정 | A사 노칭 2호기(정기 점검 TS-2026-09-0001 때), B사 롤프레스 1호기 |
| OmniSight v2.4.2 (2026-10-16) | 카메라 무한 재연결 (TS-2026-10-0002) | B사 롤프레스 1호기 (2026-10-17) |

→ 설비별 현재 버전: A사 노칭 2호기 = 2.4.1, B사 롤프레스 1호기 = 2.4.2.
같은 카메라 모듈을 쓰는 A사 설비에도 2.4.2를 적용해야 한다는 것을 이 표에서 바로 알 수 있습니다.
