# TS 업무 관리 가이드

> TS(Technical Support) 업무를 **빠짐없이 받고, 같은 방식으로 기록하고, 확실히 닫고, 다시 찾아 쓰는** 방법.
> 툴 조작법은 [사용설명서.md](사용설명서.md)를 보세요. 이 문서의 규칙은 모두 TS WorkBench에 들어 있습니다.

---

## 1. 왜 바꾸는가

| 지금 생기는 문제 | 이 방식에서의 해결 |
| --- | --- |
| 기록이 보고서·메일·개인 폴더에 흩어져 있다 | 모든 업무를 **업무 카드 1장**으로. 첨부는 카드 폴더에 모은다 |
| 같은 증상을 매번 처음부터 조사한다 | 완료 카드의 현상→원인→조치를 **지식베이스**에서 검색 |
| 업무 종류(OCR, 노칭, 조명 …)마다 양식이 다르다 | 양식은 하나. 시스템·설비는 카드의 **필드**로 구분 |
| 조치하고 나서 재발 확인을 잊는다 | 완료하면 **모니터링 후속 업무**가 자동으로 생긴다 |
| 주간 보고 쓰는 데 시간이 걸린다 | 카드에서 **주간·월간 보고, 엑셀 대장 자동 생성** |
| 내가 무엇을 얼마나 했는지 숫자가 없다 | 작업 이력으로 **현장·이동·원격 시간**, 반복 이슈 Top 5 집계 |
| 회사를 옮기면 정리 방식도 처음부터 | 데이터 폴더만 새로 만들고 **같은 방식 그대로** |

## 2. 다섯 가지 원칙

1. **연락이 오면 30초 안에 카드를 만든다.** 제목·고객사·들은 현상 한 줄이면 충분하다 (빠른 접수 `Ctrl+N`). 나중에 쓰려고 미루면 접수 시각과 첫 증상이 사라진다.
2. **카드 하나 = 문제 하나.** 한 번 출동에서 문제 두 개를 처리했으면 카드 두 장. 이어지는 일(모니터링·재방문·다른 라인 수평 전개)은 새 카드로 만들고 원본 ID를 남긴다.
3. **사실과 추정을 나눈다.** 확인 안 된 원인은 `추정:`으로 시작한다. 근거 칸에는 로그·측정값·사진처럼 다시 볼 수 있는 것만 쓴다.
4. **닫을 때는 세 가지를 확인한다.** ① 검증 결과(얼마 동안 무엇으로 확인했나) ② 재발 방지 ③ 후속 업무. 툴은 비어 있으면 경고하고, 후속 업무를 만들어 준다.
5. **기록은 당일에 끝낸다.** 현장에서 돌아온 날 카드를 채우고 현장 보고서를 만든다. 다음 날이면 수치와 순서가 흐려진다.

## 3. 업무 유형

모든 TS 업무는 아래 9가지 중 하나다. 대상 시스템(OCR, 비전, PLC, 카메라 …)은 유형이 아니라 카드의 **대상 시스템** 칸에 적는다.

| 유형 | 예 | 완료 조건 | 자동 후속 |
| --- | --- | --- | --- |
| 현장 출동 | 고객사 방문해서 현상 확인·조치 | 현장 검증 + 고객 확인 | 모니터링 |
| 원격·사무실 분석 | 로그·이미지 받아 원인 분석 | 원인 결론 + 고객 회신 | - |
| 프로그램 수정 | 버그 수정, 기능 변경, 배포 | 현장 적용 확인 + 변경 이력 | 모니터링 |
| HW 조치 | 카메라·조명·렌즈·케이블 교체·조정 | 교체 후 판정 확인 | 모니터링 |
| 정기·예방 점검 | 분기 점검, 청소, 로그 정리 | 점검표 완료 + 결과 공유 | - |
| 개선 과제 | 택트 단축, 오판정률 개선 | 효과 측정 결과 | - |
| 문의 응대 | 사용법·설정·사양 문의 | 답변 전달 | - |
| 후속 확인 | 조치 후 재발 여부 확인 | 재발 없음 확인 또는 재오픈 | - |
| 기타 | 위에 안 맞는 일 | - | - |

유형마다 **기본 체크리스트**가 붙는다 (설정에서 회사 사정에 맞게 고친다).

## 4. 상태 흐름

```
           ┌──────────────── 보류 ────────────────┐
           │  (부품 대기 · 고객 일정 · 판단 보류)  │
           ▼                                      │
 [접수] ─▶ [분석] ─▶ [조치 중] ─▶ [검증(모니터링)] ─▶ [완료]
   │                   ▲               │                │
   │                   └── 재발·실패 ──┘                │
   └─▶ [취소]                     재오픈 ◀──────────────┘
```

| 상태 | 뜻 | 다음으로 넘길 때 |
| --- | --- | --- |
| 접수 | 연락만 받은 상태 | 자료를 보기 시작하면 → 분석 |
| 분석 | 원인을 찾는 중 | 조치 방법이 정해지면 → 조치 중 |
| 조치 중 | 교체·수정·설정 변경 중 | 조치가 끝나 지켜보는 단계면 → 검증 |
| 검증(모니터링) | 조치 후 정상인지 보는 중 | 판정·생산이 정상임을 확인하면 → 완료 |
| 완료 | 검증 + 재발방지까지 끝남 | 재발하면 → 재오픈(조치 중) |
| 보류 | 내가 할 수 없는 이유로 멈춤 | 이유를 작업 이력에 꼭 남긴다 |
| 취소 | 고객 철회, 중복 접수 | - |

- `▶ 다음 단계` 버튼은 위 화살표 순서로만 움직인다. 건너뛸 때는 `상태 변경 ▾`.
- 상태를 바꾸면 **언제 무엇에서 무엇으로** 바뀌었는지 작업 이력에 자동으로 남는다 → 처리 기간이 저절로 계산된다.

## 5. 우선순위와 기한

| 우선순위 | 기준 | 첫 대응 | 기한 예 |
| --- | --- | --- | --- |
| 긴급 | 생산 중단, 불량 유출 위험 | 즉시 (당일 출동·원격) | 당일~익일 |
| 높음 | 생산 영향 있으나 우회 가능 (속도 저하, 수동 재검) | 당일 연락 | 2~3일 |
| 보통 | 간헐 발생, 생산 영향 작음 | 1일 안에 연락 | 1주 |
| 낮음 | 문의, 개선 요청 | 2일 안에 회신 | 2주 |

- **기한은 꼭 넣는다.** 기한이 없으면 대시보드 "해야 할 일"에서 맨 뒤로 밀린다.
- 기한이 지나면 대시보드와 목록에서 **빨강**, 2일 이내면 **노랑**.

## 6. 기록 작성 요령 (좋은 예 / 나쁜 예)

### 6.1 제목 — "어디 · 무엇이 · 어떻게"

| 나쁜 예 | 좋은 예 |
| --- | --- |
| A사 이슈 | 2라인 OCR 오판정 증가 |
| 카메라 문제 | 카메라 연결 끊김 후 자동 재연결 안 됨 |
| 출장 | A사 3분기 정기 점검 |

고객사·설비는 별도 칸에 있으므로 제목에 반복하지 않아도 된다. 원인을 알면 괄호로 덧붙인다: `(조명 열화)`.

### 6.2 현상 — 숫자와 비교 대상

- 나쁜 예: `오판정이 많음`
- 좋은 예: `정상 셀 NG 판정 비율 평소 0.1% → 10/12 야간조부터 2.3%. 같은 라인 1호기는 정상.`

"언제부터, 얼마나, 어디만(어디는 정상)"이 들어가면 원인 범위가 절반으로 줄어든다.

### 6.3 원인과 근거 — 5 Why

- 나쁜 예: `조명 불량`
- 좋은 예:
  - 원인: `우측 바 조명 휘도 열화 (사용 약 21,000시간)`
  - 근거: `휘도 측정 좌측 대비 62% / 예비품으로 임시 교체 시 NG 0.1% 즉시 복귀 / 5 Why: 오판정 ← 이미지 어두움 ← 우측 조명 휘도 저하 ← LED 수명 ← 교체 주기 관리 없음`

5 Why의 마지막 답("교체 주기 관리 없음")이 **재발 방지**의 재료가 된다.

### 6.4 조치 — 원복할 수 있을 만큼

- 하드웨어: 모델·S/N, 조정값
- 소프트웨어: 무엇을 바꿨는지 한 줄
- **변경 내역**: 파일·버전·설정 **전 → 후**, 백업 위치, 롤백 방법. 다음 사람이 이 칸만 보고 원래대로 되돌릴 수 있어야 한다.

### 6.5 검증 — 기간과 수량

- 나쁜 예: `정상 확인`
- 좋은 예: `교체 후 3시간(약 9,000셀) NG 0.08%, 오판정 이미지 0건, 고객 입회 확인`

### 6.6 재발 방지 — 이 카드 밖으로

이번 설비만 고친 것은 "조치"다. 재발 방지는 **다른 라인·다른 고객사·다음 점검**에서 같은 일이 안 생기게 하는 것이다.
예: `조명 15,000시간 교체 기준을 정기 점검 체크리스트에 추가`, `같은 카메라 모듈 쓰는 C사 설비에도 같은 수정 반영(별도 카드)`.

### 6.7 작업 이력 — 시간이 남는 일만

연락 수신, 통화·메일, 이동, 현장 작업, 원격 작업, 사무실 분석, 회의를 **시작~종료**로 남긴다. 한 줄 메모는 "누구와 · 무엇을 · 결과" 순서.
`10:05~11:30 원격 작업 — 검사 이미지 200장 확인, 밝기 저하 확인, 조명 의심`

## 7. 하루 · 주간 · 월간 루틴

### 매일

| 시점 | 할 일 | 툴 |
| --- | --- | --- |
| 출근 | 대시보드: 기한 지남(빨강) → 오늘 기한 → 긴급 순으로 오늘 할 일 정하기 | 대시보드 |
| 연락 올 때마다 | 30초 안에 카드 만들기 | `Ctrl+N` 빠른 접수 |
| 작업할 때 | 시작·끝 시각을 작업 이력에 | 업무 카드 › 작업 이력 |
| 현장 복귀 당일 | 현상·원인·조치·검증 채우기 → 현장 보고서 → PDF로 고객 송부 | 현장 조치 보고서 |
| 퇴근 전 | 오늘 만진 카드의 상태가 맞는지 확인, 내일 기한 확인 | 할 일 · 예정 업무 |

### 매주 (금요일 30분)

1. **모니터링·후속** 카드 정리: 재발 없으면 완료, 재발이면 원본 재오픈
2. **보류** 카드: 이유가 아직 유효한지 확인
3. 보고서 › 주간 › `업무 보고 만들기` → 팀장 보고 (HTML 또는 Notion에 MD 붙여넣기)
4. 이번 주 배포가 있었으면 프로그램 · 배포 › 설치 현황에 설치 기록이 빠지지 않았는지 확인 (주간 보고 "배포" 표)

### 매월 (월초 1시간)

1. 보고서 › 월간 → 월간 보고 + `엑셀 업무대장`
2. **반복 이슈 Top 5** 확인 → 같은 설비·시스템이 반복되면 **개선 과제** 카드 만들기
3. 지식베이스에 남길 만한 건(원인·조치가 비어 있는 완료 카드)을 채워 두기
4. 체크리스트·기준 정보 손보기 (새 고객사·설비 추가, 빠졌던 준비물 추가)
5. 프로그램 · 배포 › **설치 현황**에서 ▲ 업데이트 가능 확인 → 같은 수정이 필요한데 예전 버전인 곳이 있으면 업무 카드로 등록
6. 자동 백업 폴더에 최근 날짜 zip이 쌓이는지 확인 (백업이 안 되고 있으면 error.log 확인)

## 8. 표준 절차

### 8.1 현장 출동

**출동 전**
- [ ] 카드에 현상·발생 시점·재현 조건을 최대한 미리 받아 둔다 (사진·로그 요청)
- [ ] 지식베이스에서 같은 설비·증상 검색
- [ ] 현재 버전 프로그램·설정 백업본, 예비 부품, 케이블·노트북 준비 (체크리스트)
- [ ] 작업 이력: `이동` 시작

**현장**
- [ ] 조치 **전** 사진·화면·로그 확보 → 첨부 (`캡처 이미지 붙여넣기`)
- [ ] 조치 전 프로그램·설정 백업
- [ ] 원인 확인 → 조치 → 고객 입회 하에 검증
- [ ] 재방문이 필요하면 "재방문 필요"와 예정일
- [ ] 퇴실 전 원복 방법·연락처 공유

**복귀 당일**
- [ ] 카드 4개 영역(현상·원인·조치·검증/재발방지) 채우기
- [ ] 완료 처리 → 후속 모니터링 업무 생성
- [ ] 현장 조치 보고서 → PDF → 고객 송부, 송부한 PDF도 첨부

### 8.2 프로그램 수정

1. 변경 전 VS2022에서 커밋해 깨끗한 상태로 시작, 현장 설정 백업
2. 변경 범위·영향 검토 (같은 코드를 쓰는 다른 고객 설비?)
3. 사무실에서 **재현 데이터로** 테스트 → 결과를 검증 칸에
4. VS2022에서 커밋 (메시지 맨 앞에 업무 ID) → Release 빌드 → 업무 카드 **배포 기록** › `새 버전 배포` (버전 번호·이름표·배포본·NAS 백업 자동, 롤백은 이전 버전 폴더)
5. 현장 적용 → 동작 확인 (다른 사이트에 나중에 깔면 `③ 다른 곳에 설치 기록`)
6. **변경 내역** 칸: 파일·함수·버전 전→후, 배포·롤백 파일 위치
7. 같은 수정이 필요한 다른 설비가 있으면 별도 카드 (재발 방지 칸에 ID 기록)

코드·매뉴얼·이미지·배포 파일을 어떻게 나눠 보관하는지는 [배포관리_가이드.md](배포관리_가이드.md)를 보세요.

### 8.3 원격·사무실 분석

1. 받은 자료(로그·이미지·설정)는 카드에 첨부 또는 폴더 링크
2. 분석 시간은 작업 이력 `사무실 분석`으로
3. 결론이 나면 고객 회신 → 회신 내용을 고객 전달 사항에
4. 현장 조치가 필요하면 **새 현장 출동 카드** (원본 ID를 현상 칸에)

## 9. 지식베이스로 쓰려면

- 완료 카드의 **현상·원인·조치**만 잘 써 두면 그 자체가 지식베이스다.
- **태그 규칙**: 증상 단어 1~3개를 쉼표로. 예) `조명, 오판정` / `재연결, 통신` / `바코드, 과노출`
- 같은 증상 연락이 오면: 지식베이스 검색 → 과거 카드 ID를 새 카드 근거 칸에 적고 시작.
- 문의 응대 중 자주 오는 질문은 완료할 때 체크리스트의 "지식베이스(FAQ) 등록 여부 판단"으로 한 번 더 걸러 둔다.

---

## 10. 과거 업무 옮기기

정리 안 된 보고서·메일·폴더가 많아도 한 번에 끝낼 필요는 없다.

1. **기준 정보 먼저**: 설정에서 고객사·설비에 예전 폴더 이름에 쓰던 별칭을 넣는다 (예: `NOTCHING`, `NT2`, `노칭2`).
2. **가져오기**: 과거 자료 최상위 폴더 → 깊이 선택 → 스캔 → 날짜·제목·유형 고치기 → 등록. 원본은 그대로 두고 위치만 링크된다.
3. **중요한 것만 채우기**: 반복될 만한 건(같은 설비·같은 증상)만 카드를 열어 현상·원인·조치를 채운다. 나머지는 "언제 무엇을 했다" 기록만으로도 충분하다.
4. 앞으로 생기는 업무는 처음부터 툴로 받는다.

## 11. 다른 회사에서 쓰기

- [ ] 새 데이터 폴더 만들기 (설정 › 다른 폴더 열기 → 빈 폴더)
- [ ] 이름·부서·회사, 업무 ID 앞머리 (예: `CS`, `FS`)

- [ ] 이전 회사 데이터 폴더는 회사 보안 규정에 따라 보관 또는 반납

방식(카드 1장, 상태 흐름, 작성 요령, 루틴)은 그대로 쓴다.

### 예제 3. 정기·예방 점검 — `TS-2026-09-0001` A사 3분기 정기 점검

- 체크리스트 5개 모두 완료, 조치 칸에 청소·로그 정리 결과(디스크 여유 18%→61%)
- 고객 전달 사항: `2호기 조명 사용 시간 2만 시간 근접 → 다음 분기 교체 권장`
